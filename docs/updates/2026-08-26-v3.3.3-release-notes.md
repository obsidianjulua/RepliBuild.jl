# RepliBuild.jl v3.3.3

A patch release. Tier-2 calls got roughly 3× faster, a config key that never did
anything now does, and a fresh Linux checkout is verified by actually cloning it
rather than by reading `.gitignore`.

## Tier-2 dispatch: 53.6 ns → 17.8 ns

Every AOT thunk call was re-resolving its own symbol — a lock plus a `Dict` that
re-hashed a ~40-character mangled name, on every invocation, to find an address
that cannot change after the library is loaded. That was ~70% of the call.

Thunk addresses are resolved once now, in the wrapper's `__init__`.

| | before | after |
|---|---|---|
| `hello_message()` (returns a `String`) | 53.6 ns | **17.8 ns** |
| `hello_message_ptr()` (returns the raw pointer) | 37.8 ns | **6.8 ns** |
| first call | 4 allocations / 528 B | **1 allocation / 32 B** |

The remaining allocation is the `String` itself, and it is unavoidable: the C
side returns a pointer into the library's `.rodata`, and making a Julia `String`
means copying those bytes somewhere the GC owns. Call the `_ptr` variant if you
don't want it — that one allocates nothing, ever.

For scale: the MLIR thunk costs **2.4 ns over a bare `ccall`**. The dispatch
machinery was never the expensive part.

Verified on llamacpp (2280 call sites, real model + inference against the native
C oracle), box2d, tinyxml2, pugixml and imgui, plus a consumer-precompile probe.

## `[ingest] extra_link_libs` now actually loads libraries

It was documented as loading libraries and read by nothing — the test "covering"
it only checked that the value survived the TOML parser, which is true whether or
not the feature exists. It works now, and a new CI guard requires every config
field to be either consumed or explicitly declared inert with a reason. Nine were
inert; they are named in the changelog.

Prefer a full soname or a path (`"libfoo.so.1"`, `/opt/foo/lib/libfoo.so`) over an
`-l`-style name. On glibc ≥ 2.34, `m`/`pthread`/`dl`/`rt` are merged into libc and
`/usr/lib/libm.so` is a linker script, so `-lm` links fine while
`dlopen("libm.so")` does not.

## Building it somewhere else

`src/mlir/build.sh` now refuses a too-old toolchain instead of failing somewhere
inside CMake with an unrelated-looking error. It checks LLVM ≥ 21, that
`mlir-tblgen` and `llvm-config` come from the *same* install (several LLVM
versions side by side is the normal Debian/Ubuntu arrangement, and `PATH` order
can pick one of each — that mismatch otherwise shows up as unresolved symbols at
`dlopen` time), and that the MLIR CMake package is actually present.

`check_environment()` also stopped calling `ccall` "Tier 1". It is Tier 3.

## Platforms

**Linux x86-64 is the supported platform, and it is the only one.** The package
refuses to load anywhere else with an explicit message rather than failing
somewhere confusing later. This release adds the first real groundwork for
changing that, but nothing here should be read as Windows or macOS support.

### Windows

The struct ABI classifier used to be x86-64 SysV only. It now chooses between two
conventions, and `classifyWin64Struct` implements Microsoft x64 as a genuinely
separate algorithm — it is not a variation on SysV, and three of its four
divergences are silent ones:

- size is the only criterion: 1/2/4/8 bytes in a register, everything else
  indirect — *including* the 9–16 byte band SysV splits across two registers
- aggregates never reach XMM (`{float,float}` is `i64`; XMM0 under SysV)
- coercion is `iN` of the struct's own size, not always `i64`
- indirect arguments take no `byval` attribute

There is a test for it (95 assertions) that uses clang as a cross-target oracle,
lowering the same signatures for `x86_64-w64-windows-gnu` and comparing. And
`-DJLCS_FORCE_ABI_WIN64` builds the Win64 rules into a Linux `libJLCS.so` that
cannot run anything but can be inspected — enough to exercise the *lowering*, not
just the decision table, without a Windows machine.

**None of this has run on Windows.** The test catches an encoded rule that
disagrees with clang; it does not prove the lowering is correct on a real host,
and only a real host will. What remains after the ABI question is mostly format
and tooling plumbing rather than anything subtle: PE/COFF instead of ELF, no
`readelf` for the DWARF line tables, `LoadLibrary` instead of `dlopen`, and
`.dll` naming that is currently only half-present.

### macOS

Further out, and less work than it might look on x86-64: **macOS x86-64 uses
SysV**, so the classifier already covers it. Apple Silicon does not — that is
AAPCS, which is unmodeled, and a non-x86-64 build is now a hard `#error` rather
than a silent misapplication of x86-64 rules to a different convention.

The real obstacle on either Mac is the same as on Windows and equally unglamorous:
Mach-O instead of ELF, `.dylib` naming, and DWARF extraction that currently
shells to `readelf`. The GNU build-ID reader already degrades gracefully — it
checks the ELF magic and returns nothing otherwise — so that one is fine.

### If you want to help

The ABI classifier was the part that needed care, and Win64 is done. What is left
for either platform is mechanical: swap the binary-format tooling, and run it on
a machine that can execute the result. A contributor with a Windows or macOS box
is the missing piece, not a redesign.

## Housekeeping

`devtests.jl` runs to completion again. A testset had been asserting an absolute
count of a process-global in a suite that shares one process, and it went red when
some earlier file started creating a third JIT engine; because the suite aborts at
the first failure, everything after it had silently stopped running. It asserts a
delta now.

That fix immediately surfaced a stale expectation in a later testset, which is the
whole argument for keeping the suite green.

Two test files also skipped unavailable prerequisites by calling `exit(0)`. Inside
an `include` that ends the entire suite with a **success** status. Both are proper
skips now.

## Upgrading

No API changes. Re-wrap C++ packages to pick up the dispatch speedup — the
generated wrapper changes, the library does not, so `RepliBuild.wrap(toml)` is
enough and no rebuild is needed.

The one thing that does need a rebuild is the generated `.mlir` moving from
`tempdir()` into `<pkg>/.debug/mlir`, since it is written during the AOT thunk
build. If you want gdb to open dialect source inside a thunk, rebuild; otherwise
the wrap is sufficient.
