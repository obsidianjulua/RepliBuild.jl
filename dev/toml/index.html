The recipe

replibuild.toml is the whole interface. Everything RepliBuild does to a library — what it compiles, with which flags, from which pinned upstream, how the result is named and trimmed and presented in Julia — is decided by that file and by nothing else: there is no generator fork, no patched header, no hand-written binding layer to maintain. This page explains what the file is for and what can be done with it. Edit the TOML is the key-by-key reference.

What it is for

RepliBuild is for one situation: you have the source of a C or C++ library, and you want a Julia module that calls it. It compiles that source itself, with its own toolchain and one consistent flag set, then reads the ABI the compiler actually emitted (the DWARF debug information and the symbol table of the library it just linked) and generates the Julia module from that.

So most of what a binding needs is never written by anyone:

Who knows itWhatWhere it lives
The compilerevery type's layout, every signature, enum values, which calls throw, how each record crosses the calling conventionDWARF, read at build — never in the recipe
The source treewhich files to compile, include roots, C or C++written by discover() into the recipe
Youwhat the compiler erased or never sawthe recipe keys you add

The third row is the recipe's real content. A compiler erases macros, does not know what you mean to pass to a variadic function, cannot say who frees a returned char*, and generates nothing for a template nobody instantiated. A repository also holds tests, examples and backends that are not the library, and a build system supplies defines no header declares. Each of those is one key. A finished recipe for a large library is usually a few dozen lines, and every line in it is a fact about that library that could not be derived.

This is a developer tool that works from source on your machine. It does not replace BinaryBuilder and JLL packages, which ship prebuilt binaries for every platform. Where a recipe fits is a library you build yourself, at a version you pin, with the flags you choose — or one no JLL covers.

The loop

toml = RepliBuild.discover("path/to/project")   # write the recipe from the tree
RepliBuild.build(toml)                           # compile, link, read DWARF
RepliBuild.wrap(toml)                            # write julia/<Module>.jl
# read the wrapper, add what is missing to the recipe, build and wrap again

discover writes what a scan of the tree can see. A scan cannot see intent, so discover(force = true) rescans and keeps the keys only you can write (templates, macros, varargs, ownership, excludes, renames, dependencies, the [graph] section, platform overlays — the full list is in Edit the TOML). Once you have edited a recipe, keep it in version control and stop running discover on it.

Every key takes effect at one of two steps:

Takes effect at build (compiled into the library or its metadata)Takes effect at wrap (re-wrap only, no recompile)
[compile] flags, defines, include dirs, visibility, source_files[wrap] exclude_symbols
[link] libraries, dirs, optimisation level[wrap.rename]
[dependencies] (what is cloned, pinned, fetched, excluded)[wrap.varargs]
[types] templates, template_headers[wrap.cstring_owned]
[wrap.macros], shim_headers, shim_defines (the shim is compiled into the library)[wrap] surface_types_only, surface_types_extra, headers
[graph] targets, options, build type

build is cached on a hash of the recipe, the sources and the toolchain, so running it after any edit is cheap when nothing it reads changed.

What a recipe does not hold is as deliberate. You never write a struct layout, a signature, a calling convention, a dispatch tier or a type mapping: those are read from what the compiler did, every time, so they cannot drift from the binary. If a wrapper is wrong about one of them, that is a RepliBuild bug to report, not a key to add.

An annotated recipe

A C library from git, with each kind of residue:

[project]
name = "lua"                         # → liblua.so, module Lua, julia/Lua.jl
root = "."

[dependencies.lua]                   # the source: cloned, pinned, walked
type    = "git"
url     = "https://github.com/lua/lua.git"
tag     = "v5.4.7"
commit  = "1ab3208a1fceb12fca8f24ba57d6e13c5bff15e3"   # a moved tag is a hard error
exclude = ["onelua.c", "lua.c", "luac.c", "ltests.c"]   # the interpreter, not the library

[compile]
flags = ["-O1", "-fPIC", "-DLUA_USE_LINUX"]   # what lua's Makefile would pass

[link]
optimization_level = "2"
link_libraries     = ["m", "dl"]

[platform.windows.compile]           # the same recipe on Windows
flags = ["-O1"]
[platform.windows.link]
link_libraries = []

[wrap]
language     = "c"
shim_headers = ["lua.h", "lauxlib.h"]

[wrap.macros.lua_pop]                # a macro, compiled into a real function
ret  = "void"
args = ["lua_State*", "int"]

[wrap.varargs]                       # what you mean to pass to a variadic
proven_at       = "1ab3208a1fceb12fca8f24ba57d6e13c5bff15e3"
lua_pushfstring = [["Cstring"], ["Cint"], ["Cstring", "Cint"]]

Everything else about lua — 33 source files' worth of structs, enums, signatures and calling conventions — comes from the compile.

Recipes are shareable

A recipe names its upstream by URL and pin and holds no machine paths (relative paths resolve against the project), so it builds the same library on any machine with the toolchain. The RepliBuild-Hub is a community collection of them — lua, sqlite, zlib, pcre2, imgui, box2d, fmt, pugixml, llama.cpp, libwebp and more — and is the best place to see what real recipes look like. RepliBuild.search("xml") lists its names; to use one, copy its directory, then register it (Registry).
